# Робота з Git і код-рев'ю

## Гілки

- `main` містить стабільний код. Прямі коміти в `main` не робляться.
- Кожен учасник працює у власній гілці, яку створює від `main` для своєї задачі.
- Назва гілки: `feature/CH-<номер задачі Jira>-<коротко англійською>`, наприклад
  `feature/CH-12-backend-core`. Виправлення помилок: `fix/CH-<номер>-<коротко>`.
- Назва коміту починається з ключа задачі: `CH-12: Додати модель Course і міграції`.

## Початковий розподіл гілок

Кожна гілка змінює окремі папки, тому гілки зливаються в `main` без конфліктів.

| Гілка | Автор | Задачі Jira | Вміст |
|---|---|---|---|
| `feature/CH-21-deploy-ci` | Левченко Ренат | CH-21, CH-22, CH-28 | `docker-compose.yml`, `deploy/`, CI |
| `feature/CH-12-backend-core` | Максименко Роман | CH-12, CH-13 | Django-проєкт, застосунки, моделі, API, Celery |
| `feature/CH-23-frontend-skeleton` | Ширинга Андрій | CH-23 | каркас вебзастосунку на React і TypeScript |
| `feature/CH-14-collectors-base` | Міліщук Сергій | CH-14 | пакет збирачів: DTO, інтерфейс, реєстр, три збирачі |

## Процес роботи над задачею

1. Оновити `main` і створити гілку.
2. Реалізувати зміни невеликими комітами. Перед відправленням запустити перевірки з README.
3. Надіслати гілку й відкрити pull request у `main` за шаблоном
   `.github/pull_request_template.md`, вказавши ключ задачі Jira.
4. Рецензент перевіряє код за списком нижче та залишає коментарі.
5. Після схвалення та успішного CI автор зливає pull request (Squash and merge або Merge).
6. Задачу в Jira переводять у статус «Done».

## Хто кого перевіряє

Рецензентом не може бути автор. Щоб кожен учасник і бачив чужий код, і був перевірений,
рецензенти розподілені по колу:

| Автор pull request | Рецензент |
|---|---|
| Левченко Ренат | Максименко Роман |
| Максименко Роман | Міліщук Сергій |
| Міліщук Сергій | Ширинга Андрій |
| Ширинга Андрій | Левченко Ренат |

## Список для код-рев'ю

- Код робить те, що описано в задачі, і не містить зайвих змін.
- Дотримано принципів SOLID (див. [solid.md](solid.md)), немає залежностей від конкретних
  реалізацій там, де достатньо абстракції.
- Для нової поведінки є тести, і вони проходять.
- Лінтер і перевірка типів не повідомляють про помилки.
- У репозиторії немає секретів, паролів і ключів (вони лише у `.env`, якого немає в Git).
- Документацію оновлено, якщо змінилася структура або порядок запуску.

## Налаштування захисту main (рекомендовано)

У налаштуваннях репозиторію (Settings, Branches, Add branch protection rule) для `main` варто
ввімкнути вимогу pull request з одним схваленням і обов'язковий успішний статус перевірки `CI`.
